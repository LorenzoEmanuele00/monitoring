# Infrastructure

## Purpose
Owns globally-true technical concerns that every other context depends on: app
runtime/platform choice, secrets/credential storage, background scheduling and polling, shared
persistence, and the WidgetKit extension scaffolding shared by all Widget Kinds. A decision
lands here only if it would still need to be made even if any single domain BC didn't exist —
BC-local infra (a provider-specific adapter quirk, a widget-kind-specific cache) stays inside
the BC that owns it.

## Classification
generic — necessary and shared, but not where the product's differentiated value lives.

## Actors
None directly; every other bounded context depends on what's decided and built here.

## Ubiquitous language
Generic ops vocabulary — secret, credential store, scheduler, persistence, background refresh,
widget extension. Not yet project-specific; expect this to stay thin.

## Aggregates
None yet — this BC currently holds cross-cutting decisions, not domain aggregates.

## Key commands

## Relationships with other contexts
- **Upstream (open host) of every other context:** Project Registry, Service Integrations,
  Widgets, and Notifications all consume persistence, secrets, and scheduling from here rather
  than re-implementing their own.
- See `context-map.md` for the full picture.

## Open questions

  approach, and credential storage mechanism — tracked as `type: decision` tasks in this BC's
  `todo/`, pending the architecture foundation pass.

## Walking skeleton (infrastructure-001-walking-skeleton)
The first real code in the repo. Proves ADR-0004 through ADR-0012 wire together end-to-end for
one real Project (mise_pwa) and its three real Integrations. Xcode project generated by xcodegen
from `MissionControl/project.yml` (ADR-0013) — regenerate with `xcodegen generate` after editing
that file; both are committed.

**Identifiers:**
- App Group: `group.com.lorenzoemanuele.missioncontrol`
- App bundle ID: `com.lorenzoemanuele.missioncontrol`
- Widget extension bundle ID: `com.lorenzoemanuele.missioncontrol.widgets`
- Keychain access group: `com.lorenzoemanuele.missioncontrol.shared` (Xcode prefixes this with
  the resolved Team ID at build time; see `MCDomain.AppGroupConfig`)
- `os.Logger` subsystem: `com.lorenzoemanuele.missioncontrol` (one category per concern, e.g.
  `polling`, `persistence`, `secrets`, `ui`, `widget-timeline`)
- One Widget Kind: `com.lorenzoemanuele.missioncontrol.integrationStatus`

**Target/package layout** (`MissionControl/`):
- `MissionControl.app` — SwiftUI app target (`MissionControl/`). `MenuBarExtra` scene for
  status-bar residency + a `WindowGroup` for Project/Integration management. Owns Tier A writes,
  the polling pipeline (`Polling/PollingCoordinator.swift`), and the Connect Integration /
  Add Project UI (`Views/`).
- `MissionControlWidgets.appex` — WidgetKit extension (`MissionControlWidgets/`). Links only
  `MCSnapshot` + `MCDesignTokens` (ADR-0004) — structurally enforced via `project.yml`'s
  per-target package-product list, not just convention.
- `MissionControlKit` — local Swift package (`MissionControl/MissionControlKit/`), six library
  targets matching ADR-0004: `MCDomain` (pure model + `AppGroupConfig`/`AppGroupContainer`),
  `MCDesignTokens`, `MCSnapshot` (Tier B), `MCSecrets` (`SecretStore` + `KeychainSecretStore` +
  `InMemorySecretStore` test double), `MCPersistence` (Tier A, GRDB — app-only), `MCProviders`
  (GitHub/Firebase Hosting/Supabase adapters + `RetryPolicy`). Unit-tested with `swift test`
  (Swift Testing framework) independent of the Xcode project.

**Connect Integration flow (ADR-0012):** no OAuth. The user opens Keychain Access.app (their
login keychain, where the three mise_pwa credentials are provisioned per
`service-integrations/references/mise_pwa-credential-setup.md`), copies each credential's value,
and pastes it into `ConnectIntegrationSheet`'s field for that provider (`SecureField` for
GitHub PAT / Supabase PAT, a `TextEditor` for the Firebase service-account JSON key). The sheet
calls the matching `ProviderAdapter.validateCredential(_:)` before storing anything; only on
success does it write to `SecretStore` (keyed by the new Integration's UUID) and insert the
`ServiceIntegration` row. The user then deletes the interim Keychain Access item — MissionControl's
own Keychain storage becomes the source of truth.

**Provider adapters:** `GitHubActionsAdapter` (GitHub Actions runs REST API),
`FirebaseHostingAdapter` (does the JWT-bearer → OAuth2 access-token exchange itself via
`Security.framework` RS256 signing over the service-account key — see `JWTBearerSigner`; the
resulting access token is cached in memory only, per ADR-0012), `SupabaseAdapter` (Management
API). All three classify HTTP responses uniformly via `HTTPOutcome` (304 → not-modified,
401/403/404 → terminal, 429/5xx/network error → transient, carrying a parsed `Retry-After` /
rate-limit-reset value where present). `PollingCoordinator.pollOne` retries each transient
`PollOutcome.transientFailure` in-cycle via `RetryPolicy.run` — bounded attempts, exponential
backoff + full jitter, with the adapter's `Retry-After` honoured as a hard floor on top of the
computed delay (`RetryPolicy.run`'s `minimumDelay` parameter) — per ADR-0008. Only once retries
within one poll cycle are exhausted does the failure surface to the Integration's
`consecutiveFailureCount`/circuit-breaker state; the outer baseline/burst cadence never sees a
merely-transient blip as a failed cycle.

**Baseline cadence mechanism:** each Integration's baseline poll runs under one
`NSBackgroundActivityScheduler` instance (`PollingCoordinator.scheduleBaseline`), per ADR-0006
("so the OS can coalesce it and respect power and thermal state"). Per-provider intervals come
from `PollingCoordinator.baselineIntervals`; jitter is expressed as the scheduler's `tolerance`
(±15% of the interval) rather than a manually-computed sleep offset, letting the OS itself do the
coalescing/jitter ADR-0006 asks for.

**Provisioning caveat found while building this:** a valid codesigning identity in the login
keychain is not the same as Xcode having a signed-in developer account. `xcodebuild
-allowProvisioningUpdates` still fails with "No Accounts" until the user adds their Apple ID
under Xcode → Settings → Accounts once, interactively — no CLI/agent path around this was found.
The app + widget extension both compile cleanly with signing disabled
(`CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO`), confirming the code itself is correct; the
one-time Accounts sign-in is a manual prerequisite before a real signed build/run.
